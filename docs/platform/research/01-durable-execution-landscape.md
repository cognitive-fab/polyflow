# 01 — The Durable Execution Landscape for Agentic AI (as of 2026-09-22)

**Purpose.** Market and literature scan for a team building a credible alternative to Temporal.io focused on durable, governed execution of LLM agents for enterprises. Covers ~25 systems, then synthesizes (1) table-stakes requirements, (2) unsolved gaps, (3) Temporal's attackable weaknesses and must-match strengths.

**Method and caveats.** Web research carried out 2026-09-22. Every claim cites a URL. Primary sources (vendor docs, changelogs, GitHub issues) are preferred. Third-party blogs and aggregators are marked *(secondary)* where they are the only source; treat their numbers as indicative. Pricing changes often, so re-verify before quoting to customers.

---

## 0. Executive summary

1. **Temporal is the category leader and is pulling away commercially.** It raised a $300M Series D at $5B in Feb 2026 ([GeekWire](https://www.geekwire.com/2026/temporal-raises-300m-hits-5b-valuation-as-seattle-infrastructure-startup-rides-ai-wave/)) and a $550M Series E at $12.55B in Sept 2026, reporting a run rate above $250M that is growing more than 200% YoY ([AI Insider](https://theaiinsider.tech/2026/09/14/temporal-closes-550m-funding-round-at-a-12-55b-valuation-as-demand-surges-for-reliable-ai-infrastructure/)). The pitch is explicitly "agentic AI" ([Temporal Series D](https://temporal.io/news/temporal-raises-300M-to-make-agentic-ai-real-for-companies)). OpenAI's Codex web agent runs on Temporal ([Temporal blog](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal)), and Mistral built its enterprise Workflows product on it ([VentureBeat](https://venturebeat.com/technology/mistral-ai-launches-workflows-a-temporal-powered-orchestration-engine-already-running-millions-of-daily-executions)).
2. **The field has converged on one pattern:** deterministic orchestration code plus memoized, journaled side effects. LLM calls and tool calls are the side effects. Temporal, Restate, DBOS, Inngest, Dapr, Azure Durable Task, AWS Lambda durable functions, Cloudflare Workflows, Vercel WDK and Golem all do some version of this. The real differences are **where the journal lives** (a separate service, Postgres, an in-process library or a Wasm runtime), **how strict replay is** (full command-sequence replay or checkpoint/memoize-at-step-boundaries), and **packaging** (library, server, serverless or framework plugin).
3. **"Agent frameworks" (LangGraph, CrewAI, ADK, OpenAI Agents SDK, Microsoft Agent Framework, Mastra) offer checkpointing, not durable execution.** They save state but leave failure detection and resumption to the user ([Diagrid](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)). Most now plug into Temporal, DBOS, Restate, Dapr or Durable Task instead of competing.
4. **Nobody offers governance as a property of the execution model.** Governance here means pre-execution verification of a workflow or plan, policy enforcement bound to each effect, tamper-evident audit that can be replayed, and safe migration of in-flight agent runs. What exists today is bolted on: AWS AgentCore Policy (Cedar on gateway tool calls), Camunda's DMN guardrails, Golem's replay-deterministic authorization and Temporal's pre-release "Principal Attribution". Current academic work (Proof of Execution, FO-CTL verification of agentic deployments, pre-action verification) names exactly these gaps ([arXiv 2607.05397](https://arxiv.org/pdf/2607.05397); [arXiv 2608.03609](https://arxiv.org/abs/2608.03609); [arXiv 2609.11957](https://arxiv.org/html/2609.11957)).
5. **Temporal's weak spots for agents are structural.** They include the replay/non-determinism tax and patching; history limits of 51,200 events or 50 MB, a 2 MB payload cap and a 4 MB transaction cap; a pricing model based on per-action counts; heavy self-hosting; and no native notion of policy, plan verification or agent-aware versioning. Its strengths are equally real: battle-tested durability, polyglot SDKs, Nexus, Worker Versioning GA, multi-region/multi-cloud replication, SOC 2/HIPAA, codec-server E2E encryption, and a large ecosystem of framework integrations.

## 1. System-by-system survey

### 1.1 Temporal (the incumbent)

| Dimension | Findings |
|---|---|
| Execution model | Event-sourced **deterministic replay**. Workflow code is re-executed against Event History, and the commands it issues must match that history ([Temporal blog](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal); [Vanlightly](https://jack-vanlightly.com/blog/2025/11/24/demystifying-determinism-in-durable-execution)). |
| Determinism constraints | Workflow code cannot use randomness, wall-clock time or direct I/O. Violations cause Non-Determinism Errors (NDEs), described as "one of the most challenging parts to master" ([Long Quanzheng](https://medium.com/@qlong/myths-in-temporal-non-deterministic-errors-4e0ca7a6aa1b)). Users report NDE-stuck workflows that did not show as Failed and went unnoticed ([HN](https://news.ycombinator.com/item?id=35805130)). |
| LLM / tool calls | Run as **Activities**. Results are recorded, so replay does not re-call the model ([OpenAI Agents SDK integration docs](https://docs.temporal.io/develop/python/integrations/openai-agents)). Calling an LLM in workflow code is "the most common rookie defect" and triggers NDEs ([xgrid, secondary](https://www.xgrid.co/resources/temporal-ai-agent-orchestration-failure-patterns/)). |
| Agent integrations | OpenAI Agents SDK (public preview July 2025, then GA with sandbox support at Replay 2026) ([changelog](https://temporal.io/changelog/open-ai-agents-sdk-integration-pp); [Replay 2026](https://temporal.io/blog/replay-2026-product-announcements)). Google ADK integration is GA ([Replay 2026](https://temporal.io/blog/replay-2026-product-announcements)). There are also a LangGraph plugin ([Temporal](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)) and Pydantic AI support ([Pydantic](https://pydantic.dev/docs/ai/capabilities/durable_execution/temporal/)). In the OpenAI integration, "the agent loop, tool selection, and handoffs—runs inside the Workflow, while model calls run as Activities". MCP operations run as Activities, and nested agents (`Agent.as_tool`) stay durable. Local shell tools are unsupported and streaming does not work with local activities ([docs](https://docs.temporal.io/develop/python/integrations/openai-agents)). |
| HITL / signals | Signals, Queries, Updates. Temporal pitches these as essential actor-like building blocks ([HN, hanikesn](https://news.ycombinator.com/item?id=44842954)). "Workflow Streams" for token streaming, built on Signals and Updates, is in public preview ([Replay 2026](https://temporal.io/blog/replay-2026-product-announcements)). |
| Timers | Durable timers, schedules. |
| Versioning | Two mechanisms. (a) **Patching** (`patched()` / `deprecatePatch()`) branches code per revision and needs a three-step deploy dance before old code can be removed ([TS versioning docs](https://docs.temporal.io/develop/typescript/versioning)). (b) **Worker Versioning** is now GA. Workflows are either PINNED (stay on their original build) or AUTO_UPGRADE ([Worker Versioning docs](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning)). "Upgrade on Continue-as-New" is in public preview ([GA blog](https://temporal.io/blog/ga-worker-versioning-public-preview-upgrade-on-continue-as-new)). A fintech user called it "impossible to properly upgrade inflight workflow without manually forking" ([HN](https://news.ycombinator.com/item?id=44842954)). |
| Limits | History is capped at **51,200 events / 50 MB**, with warnings at 10,240 events / 10 MB. At the cap the server terminates the workflow ([limits](https://docs.temporal.io/workflow-execution/limits)). Payloads are capped at **2 MB** and each history transaction at **4 MB**, and neither can be changed on Cloud ([Cloud limits](https://docs.temporal.io/cloud/limits); [blob-size troubleshooting](https://docs.temporal.io/troubleshooting/blob-size-limit-error)). Continue-as-New does not carry a transcript forward ([Ably](https://ably.com/temporal/managing-conversation-history-in-a-temporal-ai-agent-chat)). |
| Agent-scale evidence | In GitHub issue #1890, a chat agent making about 100 tool calls per turn hit the 50 MB limit at around model call 53. Model inputs made up 99.8% of history. The fix was experimental External Storage or "one workflow per turn" with the conversation held in a separate DB ([sdk-python #1890](https://github.com/temporalio/sdk-python/issues/1890)). External Storage (the claim-check pattern backed by S3) is in public preview for Python and Go ([External Storage](https://docs.temporal.io/external-storage); [Replay 2026](https://temporal.io/blog/replay-2026-product-announcements)). |
| Multi-agent | Child workflows, Nexus (cross-namespace service contracts, GA) ([Nexus GA](https://temporal.io/blog/temporal-nexus-now-available)). A known pitfall: child sub-agents keep running after the parent is cancelled ([xgrid, secondary](https://www.xgrid.co/resources/temporal-ai-agent-orchestration-failure-patterns/)). |
| Observability | Web UI with event history. OpenMetrics endpoint GA and Worker Status UI in preview ([Replay 2026](https://temporal.io/blog/replay-2026-product-announcements)). OTel tracing for agents needs a "replay-safe tracer provider" ([docs](https://docs.temporal.io/develop/python/integrations/openai-agents)). |
| Enterprise | Namespaces, SAML (all plans), SCIM (GA; included on Enterprise, $500/mo add-on on lower plans), PrivateLink/PSC GA, multi-region and **multi-cloud replication GA (20-min RTO)**, Capacity Modes, and Principal Attribution (pre-release, "non-spoofable field identifying Workflow initiators") ([Replay 2026](https://temporal.io/blog/replay-2026-product-announcements); [pricing](https://docs.temporal.io/cloud/pricing)). SOC 2 Type 2, GDPR, HIPAA. Data conversion runs on customer workers, so "Temporal Cloud cannot see or decrypt your data", and a **Codec Server** decrypts in the UI without sharing keys. gRPC API audit logs can be exported ([security model](https://docs.temporal.io/cloud/security)). |
| New in 2026 | Serverless Workers on AWS Lambda (pre-release), Standalone Activities (preview), Task Queue Priority & Fairness GA, Rust SDK preview, Billing API ([Replay 2026](https://temporal.io/blog/replay-2026-product-announcements)). |
| Pricing | Consumption per **Action**: $50 per million at list, falling to $25 per million above 100M on higher tiers. Active storage costs $0.042/GBh and retained storage $0.00105/GBh. Plans are Developer ($0 or 10% of usage), Business ($500/mo or 10%), Enterprise and Mission Critical (annual). **HA applies a 2× multiplier** to actions and storage ([pricing](https://docs.temporal.io/cloud/pricing)). Starts, heartbeats and signals all count as Actions. One secondary teardown infers blended real-world pricing of about $11 per million ([dev.to, secondary](https://dev.to/beton/temporal-pricing-teardown-2026-2j11)). |
| Self-hosting pain | Needs a sharded persistence layer (Cassandra or Postgres/MySQL) plus a visibility store (Elasticsearch) and several services. It has been called "operationally serious" ([Automation Atlas, secondary](https://automationatlas.io/guides/temporal-cloud-vs-self-hosted-2026/)) and criticized for "egregious overhead and annoying multiple services" ([HN](https://news.ycombinator.com/item?id=47160065)). `numHistoryShards` is **immutable after cluster creation**, so changing it means migrating to a new cluster ([Temporal forum](https://community.temporal.io/t/numhistoryshards-modify/7585)). |
| DX pain | Steep learning curve. The same list of problems shows up repeatedly: payload limits, `datetime.now()` breaking replay, stateless classes, and signaling to dynamic IDs ([Deriv](https://derivai.substack.com/p/learning-temporal-the-hard-way)). Temporal's own State of Development 2025 report found only 1 in 4 teams describe their workflow operations as "smooth" (as cited by [Kanopy Labs, secondary](https://kanopylabs.com/blog/restate-vs-temporal-vs-dbos-durable-execution)). One commenter said Temporal "really is too heavy for a lot of use-cases" ([HN](https://news.ycombinator.com/item?id=44842954)). Absurd's author contrasts Temporal's Python SDK at about 170k LOC with Absurd's roughly 1.4k LOC TypeScript SDK ([Ronacher](https://lucumr.pocoo.org/2026/4/4/absurd-in-production/)). |

**AI-specific pitfall list** (vendor blog, *secondary*, but it matches the primary issues above): LLM calls in workflow code; missing heartbeats; unbounded agent loops blowing history; retry storms on rate limits; orphaned child agents; HITL waits without timeouts; versioning breaks when agent updates change activity sequences; observability gaps; oversized LLM outputs; third-party SDKs wrapping whole loops in one activity; no safe hook between tool output and model input ([xgrid](https://www.xgrid.co/resources/temporal-ai-agent-orchestration-failure-patterns/)).

**Derivative products:** **Mistral Workflows** (public preview, April 2026) is built on Temporal. Mistral adds streaming, payload handling, multi-tenancy and AI observability, runs the control plane itself, and keeps workers in the customer environment. Customers include La Banque Postale, CMA-CGM and ASML ([VentureBeat](https://venturebeat.com/technology/mistral-ai-launches-workflows-a-temporal-powered-orchestration-engine-already-running-millions-of-daily-executions); [Mistral](https://mistral.ai/news/workflows/)). The commentary frames this as Temporal having lacked AI-specific packaging ([beri.net, secondary](https://www.beri.net/article/mistral-workflows-temporal-enterprise-ai-orchestration-2026)). **This is direct evidence that "Temporal + AI-native layer" is a market an alternative can occupy.**

### 1.2 Restate

- **Model:** A single-binary server that **journals** every non-deterministic step: LLM calls, API requests inside tools, generated timestamps and IDs. On recovery it replays the journal and skips completed steps ([Restate durable agents](https://docs.restate.dev/ai/patterns/durable-agents); [versioning blog](https://www.restate.dev/blog/dealing-with-versioning-in-long-running-agents)). SDKs cover TypeScript, Python, Java, Kotlin, Go and Rust ([Comuvia, secondary](https://comuvia.ai/articles/durable-execution-for-ai-agents-temporal-vs-inngest-vs-restate-vs-prefect)).
- **Agent integrations:** Vercel AI SDK (`durableCalls()` middleware), OpenAI Agents (`DurableRunner`), Pydantic AI (`RestateAgent`), Google ADK (`RestatePlugin`) and LangChain middleware ([docs](https://docs.restate.dev/ai/patterns/durable-agents); [Pydantic](https://pydantic.dev/articles/restate-durable-execution-pydanticai)).
- **Sessions and multi-agent:** Virtual objects give stateful entities with concurrency control. Durable RPC, fan-out and timeouts support multi-agent patterns, and human-in-the-loop pauses are supported ([search summary of Restate docs](https://docs.restate.dev/ai/patterns/durable-agents)).
- **Versioning (the most agent-aware story in the market):** Deployments are immutable, and "every deployment is a complete, versioned snapshot of the agent: code, prompts, tool definitions, schemas, guardrails, and model configuration". Invocations are pinned to their deployment. Mismatches "fail loudly" during replay. Escape hatches let you move an in-flight invocation to a new deployment, or cancel and restart it. A registry shows in-flight counts per version ([Restate blog](https://www.restate.dev/blog/dealing-with-versioning-in-long-running-agents); [versioning docs](https://docs.restate.dev/services/versioning)). A key insight from the post is that "your code is the manual the LLM uses to interpret its own execution history" ([Restate blog](https://www.restate.dev/blog/dealing-with-versioning-in-long-running-agents)).
- **Pricing:** Restate Cloud is usage-based with a free tier. BYOC is priced by reserved processing capacity, which Restate says makes it "up to 10× cheaper at high volume than activity-priced alternatives" ([Restate pricing](https://restate.dev/pricing)).
- **Pain points:** The server is BSL-licensed rather than OSI open source ([HN](https://news.ycombinator.com/item?id=47160065)). It is a smaller company, raising a $7M seed in 2024 ([TechCrunch](https://techcrunch.com/2024/06/12/restate-raises-7m-for-its-lightweight-workflows-as-code-platform/)).

### 1.3 Inngest (+ AgentKit)

- **Model:** Event-driven step functions. Each `step.run(id, ...)` is **memoized by a hash of its string ID plus a counter**. The function re-enters from the top and completed steps return stored results ([how functions execute](https://www.inngest.com/docs/learn/how-functions-are-executed); [versioning](https://www.inngest.com/docs/learn/versioning)). Steps run as HTTP calls to your serverless or server endpoints.
- **LLM calls:** `step.ai.infer` proxies inference through Inngest's gateway, so on serverless "you don't pay for function execution while waiting" for the provider. `step.ai.wrap` wraps any SDK ([Inngest blog](https://www.inngest.com/blog/ai-orchestration-with-agentkit-step-ai)).
- **Multi-agent:** AgentKit provides **Networks** of agents with shared typed **State** and **Routers**, which can be code-based and deterministic or LLM-based. It also offers MCP tooling and a `useAgent` React hook for streaming ([AgentKit routers](https://agentkit.inngest.com/concepts/routers); [GitHub](https://github.com/inngest/agent-kit)).
- **Versioning:** Implicit. If you change code inside a step but keep its ID, in-flight runs keep the memoized result. To force re-execution you change the ID ([versioning docs](https://www.inngest.com/docs/learn/versioning)). This is lenient, but it is easy to get silently wrong. Mastra's Inngest adapter hit a bug where duplicate IDs got positional auto-indexing and "bind memoized results to the wrong logical occurrence" across suspend/resume ([Mastra #24044](https://github.com/mastra-ai/mastra/issues/24044)).
- **Pricing:** Billed per execution, where one run plus each step counts, so 5 steps = 6 executions. Hobby is free (50k executions) and Pro is $99/mo (1M executions). Enterprise adds SOC 2, HIPAA BAA, SAML, RBAC and audit trails ([pricing](https://www.inngest.com/pricing)).
- **Licensing:** The server is SSPL with delayed Apache 2.0 after 3 years; the SDKs are Apache ([GitHub](https://github.com/inngest/inngest)). Self-hosting has been supported since 1.0 ([Inngest](https://www.inngest.com/blog/inngest-1-0-announcing-self-hosting-support)). One user complaint: the TypeScript API is "a bit clunky" ([HN](https://news.ycombinator.com/item?id=44842954)).

### 1.4 DBOS

- **Model:** A library, not a server. Workflow and step checkpoints go into **your Postgres**, with no separate orchestrator ([DBOS Transact](https://www.dbos.dev/dbos-transact); [architecture](https://docs.dbos.dev/architecture)). Workflows must be deterministic, meaning the same steps in the same order, and non-deterministic operations go in steps ([workflow tutorial](https://docs.dbos.dev/python/tutorials/workflow-tutorial)). Transactional steps share the database transaction with business data, which is its unique property ([tiarebalbi, secondary](https://tiarebalbi.com/en/blog/dbos-vs-temporal-postgres-durable-execution)).
- **Versioning:** Workflows are tagged with an application version, by default a hash of the workflow source. Recovery only runs on matching versions, and blue/green draining is recommended. **Fork** re-runs a workflow from a chosen step on new code and is available in bulk from the Conductor UI ([upgrading workflows](https://docs.dbos.dev/java/tutorials/upgrading-workflows); [June 2026 update](https://www.dbos.dev/blog/new-in-dbos-june-2026)).
- **Agents:** Pydantic AI integration ([Pydantic](https://pydantic.dev/articles/pydantic-ai-dbos)). Listed as an OpenAI Agents SDK durable backend ([search summary](https://openai.github.io/openai-agents-python/running_agents/)).
- **Pricing:** Transact is free (MIT, Python/TS/Go/Java). Conductor, the ops plane, costs $99/mo (Pro, 1M checkpoints), $499/mo (Teams: RBAC, OpenMetrics, SOC 2/HIPAA) or Enterprise (self-hosted Conductor, air-gapped) ([pricing](https://www.dbos.dev/dbos-pricing)).
- **Pain points:** Critics say production effectively requires paid Conductor. They also call versioning "strange" and note there is no heartbeat or crash detection for long activities ([HN](https://news.ycombinator.com/item?id=47160065)). Features differ by language, for example the Go SDK lacks SQLite ([same](https://news.ycombinator.com/item?id=47160065)).

### 1.5 Hatchet

- A Postgres-backed task queue plus durable workflow and DAG engine. SDKs cover Python, TypeScript, Go and Ruby. Durable tasks support durable sleep and event waits. The v1 engine claims about 10k tasks/s sustained, and the MIT-licensed server can be self-hosted ([GitHub](https://github.com/hatchet-dev/hatchet); [ZenML, secondary](https://www.zenml.io/blog/inngest-alternatives)).
- **Pricing:** The first 100k task runs per month are free. Paid plans start at about $180/mo. SOC 2 and HIPAA are Enterprise-only ([Hatchet pricing](https://hatchet.run/pricing); [secondary](https://toolradar.com/tools/hatchet)).
- Its strength is DAG visualization and concurrency and rate-limit controls. It has thin agent-specific features.

### 1.6 Trigger.dev

- **Model:** Not replay. The whole container process is **checkpointed and restored with CRIU** (memory, registers, file descriptors). Waits over 5 seconds and waits on subtasks do not bill compute ([Trigger.dev docs/search](https://trigger.dev/docs/ai-chat/how-it-works); [v4 GA](https://trigger.dev/launchweek/2/trigger-v4-ga)). **Waitpoint tokens** provide HITL via a callback URL.
- **Pricing:** Billed per second of compute by machine size ($0.0000169/s to $0.00068/s) plus $0.25 per 10k runs. Enterprise adds SSO, RBAC and a SOC 2 report. It is Apache 2.0 and self-hostable, but **checkpoints, RBAC and SSO are managed-only** ([pricing](https://trigger.dev/pricing); [ZenML, secondary](https://www.zenml.io/blog/trigger-dev-pricing)).
- **Implication:** CRIU sidesteps determinism entirely. The trade-off is that a snapshot is opaque, so you cannot audit it or semantically replay it.

### 1.7 Golem Cloud

- **Model:** Wasm components. An agent is "a stateful sandbox per identity", suspends to zero, and resumes deterministically by replaying its **oplog**, a log of all external I/O. Snapshots are also taken to speed recovery ([Golem 1.5](https://golem.cloud/blog/golem-1-5-the-agent-runtime/); [GitHub](https://github.com/golemcloud/golem)). Durability is **transparent**, with no step annotations, because the runtime intercepts I/O.
- **Governance (unique):** "Authorization decisions, tool calls, and middleware behavior reproduce exactly under replay". The oplog records authorization decisions, and the permission model uses hierarchical owners with "derivation-as-attenuation" ([Golem 1.5](https://golem.cloud/blog/golem-1-5-the-agent-runtime/)).
- **Status:** Cloud is in Developer Preview. It is free with no SLA and data is wiped routinely. Paid GA was planned for Q3 2026 ([Golem pricing](https://golem.cloud/cloud/)).
- **Pain:** It requires compiling to Wasm (a language and ecosystem constraint), and the company is small.

### 1.8 Resonate

- **Model:** "Distributed Async Await", an open protocol built on **durable promises**. Each yield is a checkpoint and completed steps do not re-run. It ships as a single binary with SDKs in TypeScript, Python, Rust, Go and Java. The company raised a $3M seed in 2025 ([GitHub](https://github.com/resonatehq/resonate); [docs](https://docs.resonatehq.io/concepts/distributed-async-await); [AI Engineer](https://ai.engineer/orgs/resonate-hq-inc)).
- Notable as a *protocol-first* bet (a spec plus multiple implementations), which appeals to enterprises worried about lock-in.

### 1.9 Cloudflare Workflows + Agents SDK

- **Workflows (GA):** Step types are `step.do`, `step.sleep`/`sleepUntil` and `step.waitForEvent`. Step results are persisted ([GA blog](https://blog.cloudflare.com/workflows-ga-production-ready-durable-execution/)). Limits: 1 MiB per step result, 100 MB (Free) or 1 GB (Paid) of state per instance, 10k steps by default (up to 25k), sleep up to 365 days, and 30 days of retention for completed instances on Paid. Waiting instances do not count toward concurrency ([limits](https://developers.cloudflare.com/workflows/reference/limits/)).
- **Agents SDK:** Each Agent is a Durable Object with SQLite. `runFiber()`, `stash()` and `onFiberRecovered()` provide **checkpoint-and-notify** durability: the agent is told it was interrupted and decides how to continue ([durable execution with fibers](https://developers.cloudflare.com/agents/runtime/execution/durable-execution/); [Flue blog](https://blog.cloudflare.com/agents-platform-flue-sdk/)). Workflows integration arrived in Agents SDK v0.3.7 ([changelog](https://developers.cloudflare.com/changelog/post/2026-02-03-agents-workflows-integration)). "Project Think" adds sub-agents, sandboxed code execution and persistent sessions ([blog](https://blog.cloudflare.com/project-think/)).
- **Implication:** The fiber model admits that the application must participate in recovery. It is not transparent.

### 1.10 AWS: Step Functions, Lambda durable functions, Bedrock AgentCore

- **Step Functions:** ASL state machines. `.waitForTaskToken` pauses up to a year at zero compute for HITL ([hidekazu-konishi](https://hidekazu-konishi.com/entry/step_functions_orchestration_patterns_for_generative_ai.html); [AWS ML blog](https://aws.amazon.com/blogs/machine-learning/asynchronous-patterns-for-calling-amazon-bedrock-agentcore-agents-in-serverless-pipelines/)). AWS promotes a pattern in which "agents propose options, and deterministic code validates them before any action is taken" ([AWS Compute blog, Sept 2026](https://aws.amazon.com/blogs/compute/validating-multi-agent-decisions-with-step-functions-and-bedrock-agentcore/)). **That is a hyperscaler endorsing propose-then-verify.**
- **Lambda durable functions** (Dec 2025): checkpoint-and-replay. The function is re-invoked from the top, and completed operations return stored results. Suspension can last up to 1 year. Runtimes are Python, JS/TS and Java ([What's New](https://aws.amazon.com/about-aws/whats-new/2025/12/lambda-durable-multi-step-applications-ai-workflows/); [SDK docs](https://docs.aws.amazon.com/lambda/latest/dg/durable-execution-sdk.html)). This is AWS commoditizing Temporal's core idea.
- **Bedrock AgentCore** (GA Oct 2025): Runtime, Memory, Gateway (MCP tools), Identity (OAuth token vault), Observability, Browser and Code Interpreter. **Policy** reached GA on 2026-03-03 (Cedar rules on Gateway tool calls) and **Evaluations** GA on 2026-03-31. Pricing is consumption-only ([AgentCore GA](https://aws.amazon.com/about-aws/whats-new/2025/10/bedrock-agentcore-available); [Policy/Evals preview](https://aws.amazon.com/about-aws/whats-new/2025/12/amazon-bedrock-agentcore-policy-evaluations-preview); [clawaws, secondary](https://clawaws.com/blog/agentcore-policy-review/); [DEV, secondary](https://dev.to/akaranjkar08/amazon-bedrock-agentcore-guide-production-ai-agents-2026-2gl)). Memory gained fine-grained access control in August 2026 ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/08/agentcorememory-fine-grained-access-control/)).
- **Gap:** Policy lives at the tool gateway, which is separate from the durable orchestration (Step Functions or Lambda durable). Nothing binds "this step was authorized under policy version X" into the execution journal.

### 1.11 Azure Durable Functions / Durable Task Scheduler + Microsoft Agent Framework

- **Durable Task:** Event-sourced replay orchestrators, the same family as Temporal. **Orchestration versioning** uses `defaultVersion` in host.json, with match strategies Strict or CurrentOrOlder and mismatch strategies Reject (default; the orchestration waits for a compatible worker) or Fail ([orchestration versioning](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-orchestration-versioning)).
- **Microsoft Agent Framework 1.0** (GA 2026-04-03) has graph workflows with checkpoints at superstep boundaries, HITL and pause/resume ([MAF 1.0](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/); [checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)). Checkpoint limitations are discussed in the repo ([Discussion #2305](https://github.com/microsoft/agent-framework/discussions/2305)).
- **Durable Task extension for MAF:** Registering an agent makes it "automatically durable" with persistent sessions, backed by Durable Task Scheduler, which includes a dashboard for conversation history and orchestration visualization. On Flex Consumption, a 24-hour approval wait bills only seconds ([Durable agents](https://learn.microsoft.com/en-us/azure/durable-task/sdks/durable-agents-microsoft-agent-framework); [Azure Functions hosting](https://learn.microsoft.com/en-us/agent-framework/hosting/azure-functions)).
- **Strength:** Enterprise buyers on Azure get durability "for free" inside their existing compliance boundary. This is a real threat in Microsoft-centric accounts.

### 1.12 Google ADK / Vertex AI Agent Engine

- **ADK:** `ResumabilityConfig(is_resumable=True)` pauses on long-running function calls and resumes "from the last event, if it's paused or failed midway through" ([ADK resume](https://google.github.io/adk-docs/runtime/resume/)). Pitfall: `SequentialAgent` re-executes all sub-agents after a `LongRunningFunctionTool` resume ([adk-python #3348](https://github.com/google/adk-python/discussions/3348)). Diagrid argues ADK "relies on external failure detection" ([Diagrid](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)).
- **Agent Engine:** Managed runtime; Sessions and Memory Bank are GA. Pricing is $0.0864/vCPU-h, $0.009/GB-h and $0.25 per 1k session or memory events; Sessions and Memory Bank became billable on 2026-01-28 ([nerova, secondary](https://nerova.ai/costs-roi/vertex-ai-agent-builder-pricing-explained-2026); [Google blog](https://cloud.google.com/blog/products/ai-machine-learning/vertex-ai-memory-bank-in-public-preview)). Tool governance additions are covered on the Google blog ([Google](https://cloud.google.com/blog/products/ai-machine-learning/new-enhanced-tool-governance-in-vertex-ai-agent-builder)).
- Temporal and Restate both ship ADK durability plugins, so Google has effectively outsourced true durability to them ([Replay 2026](https://temporal.io/blog/replay-2026-product-announcements); [Restate](https://docs.restate.dev/ai/patterns/durable-agents)).

### 1.13 LangGraph / LangSmith Deployment

- **Model:** Checkpointers save graph state at every superstep, keyed by thread. They enable memory, fault recovery, **time travel** and HITL ([LangGraph](https://github.com/langchain-ai/langgraph); [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)).
- **Interrupt semantics pain:** On resume, **the node re-executes from the start**, so side effects that ran before `interrupt()` fire again. Multiple interrupts in one node misbehave. The recommendation is one side effect per node ([raed.dev](https://blog.raed.dev/posts/langgraph-hitl/); [#6208](https://github.com/langchain-ai/langgraph/issues/6208); [#7780](https://github.com/langchain-ai/langgraph/issues/7780); [#9002](https://github.com/langchain-ai/langgraph/issues/9002); [#4796](https://github.com/langchain-ai/langgraph/issues/4796)).
- **Platform:** LangGraph Platform was renamed LangSmith Deployment (Oct 2025). Pricing is $39/seat/mo on Plus, about $0.001 per node executed, and standby uptime at about $0.0036/min in production ([truefoundry, secondary](https://www.truefoundry.com/blog/langgraph-pricing); [ZenML, secondary](https://www.zenml.io/blog/langgraph-pricing)).
- Temporal ships a LangGraph plugin, which is again evidence that frameworks lean on engines ([Temporal](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)).

### 1.14 CrewAI Flows / AMP

- `@persist` saves Flow state to a DB for crash-resume and human-input waits. It is recommended on a terminal step, because class-level persist snapshots mid-run ([CrewAI docs](https://docs.crewai.com/en/concepts/production-architecture)). There is no automatic restart, and users must write skip logic ([Diagrid](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)). **CrewAI AMP** adds managed deployment, observability, governance and support ([CrewAI AMP](https://blog.crewai.com/crewai-amp-the-agent-management-platform/)).

### 1.15 Mastra

- Workflows suspend and resume through **snapshots** saved to configured storage ([suspend/resume](https://mastra.ai/docs/workflows/suspend-and-resume); [snapshots](https://mastra.ai/docs/workflows/snapshots)). Durability can be delegated to Inngest. Open bugs show the fragility of this layering: step-ID collisions across loop iterations and resumes ([#24044](https://github.com/mastra-ai/mastra/issues/24044)), and approval rejected when the snapshot is large ([#22413](https://github.com/mastra-ai/mastra/issues/22413)). A fix was needed so a suspension is only announced after its snapshot is durable ([PR #22445](https://github.com/mastra-ai/mastra/pull/22445)).

### 1.16 Pydantic AI (durable execution integrations)

- Officially supports **Temporal, DBOS, Prefect and Restate**. The integrations are co-maintained and use only public interfaces. They turn model requests and tool calls into activities or steps ([overview](https://pydantic.dev/docs/ai/integrations/durable_execution/overview/)). There is a docs page on *building a durable execution backend* ([backends](https://pydantic.dev/docs/ai/capabilities/durable_execution/backends/)). An open proposal would add a first-class `RuntimeCapability` extension point ([#5477](https://github.com/pydantic/pydantic-ai/issues/5477)). **This gives a new engine a cheap route to distribution.**

### 1.17 OpenAI Agents SDK and OpenAI Agents API

- **SDK:** `RunState` is the "durable pause/resume boundary" for HITL. It serializes to JSON and is restored later, and Sessions hold history ([RunState](https://openai.github.io/openai-agents-python/ref/run_state/); [HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)). Durable execution integrations exist for Temporal, Dapr, Restate and DBOS ([running agents](https://openai.github.io/openai-agents-python/running_agents/)).
- **Agents API** (public beta 2026-09-10): OpenAI productized the Codex harness. It offers durable sessions, context compaction, failure recovery, subagents, and hosted or bring-your-own sandboxes. **Data residency is US-only and Zero Data Retention (ZDR) is not supported** at launch ([XenoSpectrum, secondary](https://xenospectrum.com/en/openai-agents-api-codex-runtime/); [paragraph, secondary](https://paragraph.com/@coinpower/openai-agents-api-long-running-work)). Model vendors are moving into the "agent runtime" layer, but only for their own models and with weak residency.
- **Anthropic Claude Managed Agents** is the analogous product. It separates the harness, the sandbox and a **durable event log**. Recovery happens via `wake(sessionId)` from the last event ([Claude docs](https://platform.claude.com/docs/en/managed-agents/overview); [Cobus Greyling, secondary](https://cobusgreyling.substack.com/p/how-claude-managed-agents-actually)).

### 1.18 Dapr Agents / Dapr Workflow

- **Dapr Agents v1.0 GA** was announced 2026-03-23 at KubeCon EU through CNCF, built with NVIDIA. It offers durable workflows, state across more than 30 stores, **SPIFFE identity**, multi-agent messaging and observability ([CNCF](https://www.cncf.io/announcements/2026/03/23/general-availability-of-dapr-agents-delivers-production-reliability-for-enterprise-ai/)). Dapr Workflow is replay-based like Durable Task ([Diagrid](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)).
- **Strength:** Vendor-neutral CNCF governance plus workload identity. **Weakness:** Kubernetes and sidecar operational weight, and it is Python-first for agents.

### 1.19 Letta

- A stateful-agent server where "the server owns all state" in Postgres. Memory blocks, the **Agent File (.af)** open format for serializing and checkpointing agents, and sleep-time agents ([Agent File](https://docs.letta.com/guides/core-concepts/agent-file); [sudoall, secondary](https://sudoall.com/letta-stateful-agents-nodejs/); [sleep-time](https://docs.letta.com/guides/agents/architectures/sleeptime/)). Pricing: API plan at $20/mo plus $0.10 per active agent per month; Apache 2.0 ([Letta pricing](https://docs.letta.com/pricing); [secondary](https://dreaming.press/stack/letta-cloud)). It focuses on memory, not workflow durability or governance.

### 1.20 Prefect / ControlFlow / Marvin

- Prefect 3 brought **transactional semantics**, grouping tasks into atomic units with rollback and cache-key-based execution ([Prefect 3](https://www.prefect.io/blog/introducing-prefect-3-0)). ControlFlow was archived and merged into Marvin 3.0 ([ControlFlow archive](https://github.com/prefect-archive/ControlFlow)). Prefect is a Pydantic AI durable backend ([Pydantic](https://pydantic.dev/docs/ai/integrations/durable_execution/overview/)). The **rollback/compensation** idea is underused by agent platforms.

### 1.21 Camunda (BPMN + agentic orchestration)

- **AI Agent connector plus ad-hoc sub-process.** The LLM chooses among BPMN tasks inside an ad-hoc sub-process. Camunda 8.8 (October 2025) delivers "enterprise-grade agents" blending deterministic flows and dynamic agents ([AI agents docs](https://docs.camunda.io/docs/components/agentic-orchestration/ai-agents/); [Camunda 8.8](https://camunda.com/blog/2025/10/enterprise-grade-agentic-automation-is-here/)). Guardrails include HITL, **policy via DMN**, audit logs, override paths and tool gatekeeping ([guardrails blog](https://camunda.com/blog/2026/01/guardrails-and-best-practices-for-agentic-orchestration/)).
- **Strength:** The model is visible and auditable (BPMN), and business stakeholders can read it. **Weakness:** BPMN is heavy for developers, and the "agent" is a black box inside one sub-process.

### 1.22 Orkes Conductor + Agentspan

- Conductor OSS (from Netflix) supports JSON-defined workflows with native LLM and MCP tasks, human tasks and inspectable history ([Orkes AI](https://orkes.io/content/devguide/ai)). **Every execution snapshots the workflow definition at start**, so changing a definition does not affect running executions. Restarts can optionally use the latest definition ([Conductor versioning](https://docs.conductor-oss.org/devguide/how-tos/Workflows/versioning-workflows.html); [Orkes blog](https://orkes.io/blog/workflow-versioning-and-backward-compatibility-in-conductor/)). Orkes offers SSO, RBAC over workflows, secrets and prompts, audit logs and SOC 2 Type 2 ([Orkes RBAC](https://orkes.io/content/category/access-control-and-security); [Orkes Select](https://orkes.io/orkes-select)). It raised $60M in April 2026 ([BusinessWire](https://www.businesswire.com/news/home/20260423550324/en/Orkes-Raises-$60M-as-Developers-Increasingly-Use-Its-Platform-to-Deploy-AI-Confidently-in-Production)).
- **Agentspan** (MIT) compiles an agent definition into a Conductor workflow. In its **Plan-Execute** mode, "the LLM decides what to do at runtime; Conductor locks it in and executes it deterministically — the planner emits a JSON plan once that gets compiled into an immutable Conductor sub-workflow". Guardrails (regex, LLM-as-judge or custom) each have four failure modes: retry, raise, auto-fix or escalate to a human. `@tool(approval_required=True)` marks tools that need approval, and it offers deterministic tests with no LLM calls ([Agentspan GitHub](https://github.com/agentspan-ai/agentspan); [Orkes blog](https://orkes.io/blog/open-sourcing-agentspan-durable-ai-agents)). **This is the closest existing product to "LLM proposes a workflow, engine executes it deterministically"**, but it has no formal verification of the plan before execution.

### 1.23 Kestra

- Declarative YAML orchestration. Kestra 1.0 (LTS) adds an `AIAgent` task, with LLM, memory and tools, inside flows that provide retries, timeouts, approval gates and execution history, plus an AI Copilot that generates YAML ([Kestra 1.0](https://kestra.io/blogs/release-1-0)). The Enterprise edition has RBAC, SSO/SCIM, audit logs, multi-tenancy, worker isolation and air-gapped deployment ([Kestra EE](https://kestra.io/docs/enterprise)). **Declarative flows are statically inspectable**, which is a base for verification, but Kestra does not verify them.

## 2. Cross-cutting comparison

### 2.1 Execution model taxonomy

| Model | Who | Determinism burden | Audit/replay quality | Versioning consequence |
|---|---|---|---|---|
| **Full deterministic replay** (command sequence must match history) | Temporal, Azure Durable Task, Dapr Workflow, Mistral WF | High: the whole workflow body | Highest. The history is a complete causal record | NDEs; patching or pinning required |
| **Journal/memoize at step boundaries** (re-enter from top, skip completed steps) | Restate, DBOS, Inngest, Lambda durable, Cloudflare Workflows, Vercel WDK, Absurd, Resonate | Medium: step order and IDs must be stable | Good at step granularity; control flow between steps is not recorded | Step-ID/order drift silently mis-binds results ([Mastra #24044](https://github.com/mastra-ai/mastra/issues/24044)); pinning (Restate, DBOS) or ID changes (Inngest) |
| **Transparent I/O oplog** | Golem (Wasm) | None for the user; the runtime intercepts I/O | High, including auth decisions | Tied to component versions |
| **Process snapshot** | Trigger.dev (CRIU) | None | Low. Snapshots are opaque | Snapshot tied to the image |
| **State checkpoint per node/superstep** | LangGraph, MAF workflows, CrewAI, Mastra, ADK, OpenAI RunState | None, but side effects re-fire | Medium: state snapshots with no effect ledger | Mostly unaddressed |
| **Definition-snapshot interpreter** (JSON/YAML/BPMN interpreted by the engine) | Conductor/Orkes, Camunda, Kestra, Step Functions | None for user code; the definition is data | High and legible | Definition snapshot per run; clean |

**Key insight.** Interpreter-style engines (Conductor, Camunda, Step Functions, Kestra) avoid the determinism tax and make versioning and audit legible, because the workflow is **data**, not code. Code-first engines win developer mindshare but pay the NDE and versioning tax. An agent platform in which the LLM *emits* a workflow (data) that a deterministic engine interprets, as Agentspan's Plan-Execute does, gets the benefits of both. It also creates a natural checkpoint where the plan can be **verified before it runs**.

## 3. Synthesis

### 3.1 Requirements matrix: enterprise "table stakes" for a durable agent platform (2026)

| # | Requirement | Why it is table stakes (evidence) |
|---|---|---|
| R1 | **Exactly-once-effect semantics for LLM and tool calls**: memoized results, idempotency keys, no re-billing tokens on recovery | Every serious engine does this ([Restate](https://docs.restate.dev/ai/patterns/durable-agents); [Temporal](https://docs.temporal.io/develop/python/integrations/openai-agents)). LangGraph's double-execution is a widely reported bug class ([raed.dev](https://blog.raed.dev/posts/langgraph-hitl/)). |
| R2 | **Automatic crash recovery** with no user-written resume logic | This is the "checkpoints ≠ durable execution" critique ([Diagrid](https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows)). |

| R16 | **Regulatory logging** of automatic, lifetime event logs for AI systems | EU AI Act Art. 12 ([text](https://artificialintelligenceact.eu/article/12/)). High-risk obligations are deferred to 2 Dec 2027 (Annex III) and 2 Aug 2028 (Annex I) by the Digital Omnibus ([Gibson Dunn](https://www.gibsondunn.com/eu-ai-act-omnibus-agreement-postponed-high-risk-deadlines-and-other-key-changes/)), so buyers are planning for it now. |

| R18 | **Polyglot SDKs**, at minimum Python and TypeScript, with Go and Java for the enterprise backend | Temporal, Restate and DBOS all cover four or more languages. |

### 3.2 Gaps and unsolved problems (the whitespace)

**G1. The determinism ↔ "smartness" tension is managed, not solved.** The industry consensus puts the LLM in a memoized side effect and keeps control flow deterministic ([Temporal](https://temporal.io/blog/of-course-you-can-build-dynamic-ai-agents-with-temporal); [Vanlightly](https://jack-vanlightly.com/blog/2025/11/24/demystifying-determinism-in-durable-execution)). But in an agent loop *the LLM output is the control flow*: it picks the next tool, the next sub-agent, whether to stop. So:
- Replay reproduces *what happened*, but gives no evidence about *whether it was allowed* or *what the agent would do now*. It is a tape, not a model.
- Changing the prompt or model, or the tool schema, silently changes how the recorded history should be *interpreted*. Restate states this outright ("your code is the manual the LLM uses to interpret its own execution history") and answers only with pinning ([Restate](https://www.restate.dev/blog/dealing-with-versioning-in-long-running-agents)).
- No engine distinguishes the **decision** (a proposed action as data) from the **effect** (the execution) as first-class, separately checkable events. Temporal histories record Activity results, not the "LLM proposed X; policy Y allowed it; effect Z executed" chain. The Proof of Execution paper names this missing binding: "lack of binding between authorization contracts and actual execution traces, absence of tamper-evident audit trails" ([arXiv 2607.05397](https://arxiv.org/pdf/2607.05397)).
- **Opportunity:** a runtime whose journal is a *typed decision ledger* (proposal → policy verdict → effect → observation), in which the deterministic core is a **verifiable state machine** and the LLM is confined to proposing transitions.

**G2. No verification of workflows or plans before they run.** Code-first engines (Temporal, Restate, DBOS, Inngest) cannot statically reason about what a workflow can do. Their only safety net is the NDE at replay time, which comes *after* deploy. Interpreter engines (Conductor, Kestra, Camunda, Step Functions) have inspectable definitions, but at most they validate syntax. The closest things are Agentspan's "compile the LLM's JSON plan into an immutable sub-workflow" ([Agentspan](https://github.com/agentspan-ai/agentspan)) and AWS's "agents propose, deterministic code validates" blog pattern ([AWS](https://aws.amazon.com/blogs/compute/validating-multi-agent-decisions-with-step-functions-and-bedrock-agentcore/)). Neither does model checking against invariants. Research is moving here: FO-CTL verification of stateful tool-enabled agent deployments (PSPACE-complete under finite-domain restrictions) ([arXiv 2608.03609](https://arxiv.org/abs/2608.03609)); AgentSPEX declarative specs amenable to static and runtime verification ([arXiv 2604.13346](https://arxiv.org/pdf/2604.13346)); LTL trace verification (AgentLTL) ([arXiv 2607.02599](https://arxiv.org/pdf/2607.02599)); and pre-action verification that catches 95.8% of invalid commands at a 10% false-positive rate ([arXiv 2609.11957](https://arxiv.org/html/2609.11957)). **No commercial durable engine ships any of this.**

**G3. Governance and policy enforcement live outside the execution journal.** AgentCore Policy enforces Cedar at the tool gateway ([clawaws, secondary](https://clawaws.com/blog/agentcore-policy-review/)). Camunda uses DMN ([Camunda](https://camunda.com/blog/2026/01/guardrails-and-best-practices-for-agentic-orchestration/)), and Agentspan and Kestra use guardrail hooks. Temporal has only just started with "Principal Attribution" (pre-release) ([Replay 2026](https://temporal.io/blog/replay-2026-product-announcements)). Only Golem records authorization decisions in the replayable log ([Golem](https://golem.cloud/blog/golem-1-5-the-agent-runtime/)). Missing everywhere:
- **Policy-version pinning.** Which policy version authorized each effect, and can the decision be re-evaluated under a new policy (a "what-if" replay)?
- **Delegated authority for sub-agents.** Attenuation when a parent spawns a child agent; only Golem has "derivation-as-attenuation".
- **Budget and blast-radius limits as enforced invariants.** Token or cost ceilings, max tool calls, and forbidden tool sequences, enforced as invariants rather than retry configuration. Temporal users hit "retry storms that consume API budgets" ([xgrid, secondary](https://www.xgrid.co/resources/temporal-ai-agent-orchestration-failure-patterns/)).
- **Tamper-evident, exportable audit** (hash-chained journals) aimed at EU AI Act Art. 12-style lifetime logs ([Art. 12](https://artificialintelligenceact.eu/article/12/)).

**G4. Safe versioning of in-flight *agent* runs is primitive.** The state of the art is (a) pin to the old build and keep old workers alive (Temporal PINNED, Restate, DBOS, Conductor), (b) branch in code (Temporal patching), or (c) move or fork by hand (Restate, DBOS). Nobody offers:
- **Compatibility classification of a change** that says, before deploy, whether in-flight runs at state S can safely migrate. (This is exactly what state-machine-level analysis can do and replay-level engines cannot.)
- **State migration functions** checked against invariants, rather than "restart from step N and hope".
- **Versioning of non-code agent artifacts** (prompt, model, tool schema, policy) as first-class, independently rolled dimensions. Restate bundles them into one immutable deployment ([Restate](https://www.restate.dev/blog/dealing-with-versioning-in-long-running-agents)); everyone else ignores them.
- A fintech practitioner's summary of the status quo: "impossible to properly upgrade inflight workflow without manually forking" ([HN](https://news.ycombinator.com/item?id=44842954)).

**G5. Multi-agent and human coordination semantics are ad hoc.** What exists: child workflows, Nexus contracts, AgentKit routers and shared state, and Restate virtual objects. What is missing:
- Typed, versioned **inter-agent protocols** with verified compatibility across parent and child versions.
- **Cancellation and compensation propagation**. Orphaned sub-agents are a known Temporal pitfall ([xgrid, secondary](https://www.xgrid.co/resources/temporal-ai-agent-orchestration-failure-patterns/)), and Prefect-style transactional rollback ([Prefect 3](https://www.prefect.io/blog/introducing-prefect-3-0)) has not been carried over to agents.
- **Humans as first-class actors** with identities, SLAs, delegation and escalation, rather than "a signal with a timeout". The LangGraph interrupt re-execution bugs show how fragile the HITL mechanics still are ([#6208](https://github.com/langchain-ai/langgraph/issues/6208)).

**G6. The unbounded-history problem for conversational agents.** Agents naturally produce N² history growth (each call re-sends the context) ([#1890](https://github.com/temporalio/sdk-python/issues/1890)). The fixes today are claim-check storage, one workflow per turn, and Continue-as-New, which drops the transcript ([Ably](https://ably.com/temporal/managing-conversation-history-in-a-temporal-ai-agent-chat)). None of these is a principled separation of *control state* (small, replayed, verified) from *context state* (large, content-addressed, compacted).

**G7. Economic model mismatch.** Per-action and per-step billing penalizes fine-grained journaling (see §2.3). Enterprises want cost attribution per agent, tenant or business outcome, and hard budget enforcement. Nobody sells "governed runs".

**G8. Operability by small teams, and by agents themselves.** Absurd and Kitaru converge on agent-legible ops interfaces (skills, MCP servers, CLI inspection) ([ZenML](https://www.zenml.io/blog/where-durable-execution-is-headed); [Ronacher](https://lucumr.pocoo.org/2026/4/4/absurd-in-production/)). Temporal's self-host footprint is the opposite (§1.1).

**Strategic reading.** Competing with Temporal on raw durability is a losing position given the capital gap and the commoditization by AWS Lambda durable functions, Azure Durable Task, Cloudflare and Vercel. The defensible wedge is the layer Mistral had to build *on top of* Temporal, taken further into **governance by construction**:
1. a verifiable deterministic core (a state machine or declared plan), in which the LLM proposes and the engine disposes;
2. pre-deploy and pre-run verification (invariants, model checking, compatibility classification of versions against the live fleet);
3. a decision-ledger journal (proposal → policy verdict → effect → observation) that is tamper-evident and replayable under alternative policies;
4. agent-artifact versioning with verified in-flight migration;
5. interop and adapters for OpenAI Agents SDK, ADK, LangGraph, Pydantic AI and MCP, and possibly an adapter that *runs on* Temporal (as Mistral and Agentspan-on-Conductor do), so buyers need not rip out their existing engine.
