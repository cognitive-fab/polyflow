polyflow

Agent-driven deploys, with the gates CI can't give you

My CI deliberately refuses to deploy the backend, so I do it from an agent instead. That path had no gates at all. Here is how I gave it some.

The pipeline for a production app I run is ordinary: commit, CI, automatic sandbox deploy, manual promotion to production. The promotion is well guarded — the ref has to be an ancestor of main, the suite re-runs at that exact commit, a smoke check runs after the deploy, and only then is the commit tagged, because that tag is the rollback target.

All of that is for the frontend. When a change touches the backend, CI stops on purpose: the deploy role it holds is frontend-only by design, and a full backend build on a shared runner takes longer than it is worth. It prints the command and tells me to run it from a workstation.

So I run it from an agent. And at that moment every gate disappears. No ancestry check, no re-run at the promoted commit, no enforced smoke, no tag, no record. The riskiest deploy path in the project is the only one with nothing watching it.

One work order at a time

polyflow is an MCP server that runs a workflow — a small state machine — and hands the agent a single instruction at a time. The agent runs the command itself, with its own credentials and its own approval prompts. polyflow has neither. It decides what comes next, records what happened, and refuses anything out of order.

The run is identified by the commit, derived from validated input rather than named by the model. Asking twice for the same commit re-attaches to the run in progress instead of deploying again — which matters, because the deploy script ends with a CDN invalidation, and that is the one step that must never happen twice.

The rules, and what they are worth

A workflow ships with rules that must hold on every path it can take. Before it loads, polyflow walks every reachable path and checks each one. For the promotion that is seven paths across fourteen states:

  • no prod deploy without an ancestry check
  • no prod deploy without tests passing at this commit
  • no prod deploy without an approval
  • at most one prod deploy per path
  • no tag without a passing smoke check
  • at most one tag per path
  • smoke implies a prior deploy

None of these are inventions. They were already written in the project's own CI documentation, in prose, describing what the frontend path does. Moving them into a workflow only made them apply to the path that was never covered.

The checker refused my first version

I wrote an eighth rule: exactly one test run per promotion. It sounded right. The gate refused the workflow and handed back the path that broke it:

VIOLATION 'exactly-one-test-run-when-started' path : START() → ANCESTRY_FAILED(not-an-ancestor-of-main) emitted: check_ancestry@1

A promotion that fails the ancestry check never reaches the suite — and shouldn't. My rule was wrong, not the machine. It became at most one, plus a new rule that tests imply a prior ancestry check, and the workflow was admitted.

What it does not do

  • It does not test your code. It enforces order, single execution, and an approval. A compliant workflow can still ship something broken if the suite passes and shouldn't have.
  • It constrains the run, not the agent. If the agent runs the deploy command outside the workflow, nothing stops it. The rules govern work orders.
  • It is a consistency check, not a proof. Exhaustive means exhaustive over the values the workflow declares.

Worth it for the record alone

Every step of every deploy is journaled — accepted or rejected, with reasons. A workstation deploy has never had that. Even setting the gates aside, being able to answer "who approved which commit going to production, and did the smoke check pass before it was tagged" is worth the afternoon it took.
