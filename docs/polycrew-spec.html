polycrew · specification · draft 4

Many hands,
one journal

polycrew is the multi-participant layer over polyflow. How several agents — and the people among them — work one run at the same time, how they wait for each other, and how what they did becomes a record nobody has to take on faith. Every coordination is a journaled step of a machine that was checked before it loaded. Agents never talk to each other; they talk to the run.

grounded in polyflow src/ and polyrun FR-1–FR-8 child machines are shipped (kernel.mjs:476, test/m2.test.mjs) 26 Aug 2026
0 · The problem

Today one agent holds one run. Nothing stops a second agent — and nothing helps it.

polyflow already returns next as an array: a step may emit several work orders at once, and a single agent works through them. Two agents attached to the same run would both see the same open orders, both run the same tool, and both report — the second report lands as order-expired or a stale-completion reject, which is safe, and wasteful. There is no way to say this order is mine, no way to say only a reviewer may take this one, no record of who did a step, and no way for a run to wait until three sub-tasks are done before it continues.

There is also a structural constraint the current build hides. Each host spawns bin/polyflow-mcp.mjs over stdio, so each agent session gets its own process, and the broker’s order map is in that process’s memory (broker.mjs:19). Two agents on one SQLite file are two brokers that cannot see each other’s parked orders. Multi-agent starts with one broker per instance area.

The good news is that almost everything needed already exists one layer down. polyrun has atomic dispatch with a per-instance row lock, deduped completions, leases on effect intents, timers, and — since M2 — child machines with completion actions and a product checker. This spec adds the thin layer that lets agents use those primitives, and the vocabulary that lets a workflow author say which agent may do what.

0b · Two packages, one gate

Why polycrew is separate, and exactly where the seam falls

Almost everything below scales down to one agent for free: roles are optional and a role-less order goes to the starting actor, attach and next are additive, journal columns are constant at n=1. One thing does not, and it is the reason for two packages.

polyflow today runs as a stdio process the host spawns per session, with the broker’s order map in that process’s memory (broker.mjs:19). No daemon, no port, no lifecycle — which is what makes it installable in five hosts. Many actors need one broker per instance area, and that is a different deployment shape. The fork is not one agent versus many; it is in-process broker, stdio, SQLite versus shared broker, service, Postgres.

So: polyflow stays the single-participant engine and the library. polycrew depends on it, and must never fork the admission gate — it imports Library.certify and adds the product and structural checks. Two gates would mean the guarantee stops being one sentence.

Lands inWhat
polyflowFan-out and join (MA-10, MA-13) — a single agent driving a parent with children is an ordinary single-agent workflow; this is workflow structure, not coordination. The waiting-state timer check (MA-11). Journal actor, order_id, provenance columns (MA-14). workflow_progress and workflow_report_run (MA-15, MA-16). Host events (MA-17).

Settled (draft 4). Neither route in the earlier draft survives contact with the MVP. The broker is elected, not deployed — see MA-22. Nothing is installed, SQLite stays, and the store keeps exactly one writer.

The boundary, named

polycrew depends on polyflow as a library and supplies two of its four exports. Both refactors are additive and can be built and tested in polyflow before polycrew exists, which is how the seam gets proved while there is still only one package.

1 · Principles

Six rules everything below follows from

The run is the only shared state

Agents synchronize through actions on a machine and nothing else. No blackboard, no scratchpad, no message bus. If two agents need to agree on something, that something is a state key, and the agreement is a journaled step.

A join is verified logic, not runtime logic

“Wait until all three are done,” “two distinct reviewers must approve,” “give up after an hour” are acceptors and timers in a contract that the admission gate explored. Nothing in polyflow’s code decides when a barrier opens.

Identity is derived, never chosen

Runs already derive their key from validated input. Children derive theirs the same way from the data that spawned them. An agent cannot start a second copy of a sub-task by inventing a name (FINDINGS-phase3 §6, extended).

Every step names its actor

Who claimed, who reported, who signalled — on the journal row. The journal already answers what happened; it now answers who did it, which is what a report is.

polyflow still calls no tool

The inversion holds with many agents exactly as with one: each agent runs its tools under its own credentials and gates. polyflow hands out orders and records results. It never acquires a connector because there are more agents.

No model on the coordination path

Whether a join has opened, whether a report is a duplicate, whether an order may be claimed — all deterministic. A model decides how to fulfil an order; never whether the run may proceed.

What determinism claims: given the sequence of accepted actions the state is a function of them, and the journal reproduces it on any machine. Which actor claimed which order is not deterministic — it is first-come against wall-clock arrival — and does not need to be. The outcome must not depend on who got what; the journal records who did.

2 · Vocabulary

Six words, three of them new

TermMeaning
actornewOne running participant, identified as {agent area}/{actor id}. The agent area is the class (areas.mjs); the actor id is the running copy and nothing else — one CLI session, one worker, one person. Not a persona: a persona is a class. Supplied on every write call.
human actornewAn actor whose agent area names a human channel: human/jjdub. It participates exactly as an agent actor does — claims orders, reports, is journaled — but its writes arrive from the host’s answer channel rather than from a model, and its orders obey different lease physics (MA-18).
rolenewA name a workflow gives to a kind of participant (gatherer, reviewer). Work orders are addressed to roles, never to an actor. A role may require an actor kind or agent area. An actor declares which roles it can play when it attaches.
work orderextendedAs today (broker.mjs), plus role, claimed_by, claimed_until. Still one polyrun effect intent; the claim is a lease on that intent, so it survives a crash for free.
child runshippedA polyrun child machine (FR-8) spawned by the parent’s effect mapper, with its own contract, journal and orders. Its terminal state dispatches a completion action into the parent. This is fan-out.
joinshippedNot a primitive. A state in the parent whose acceptors count completions and move on when the workflow’s rule says so. Checked by polyrun check-product with authored cross-machine invariants.

Three tiers, not two. POLYFLOW_AGENT is the class, POLYFLOW_INSTANCE is the workspace that scopes the store, and the actor is a third thing: the running copy inside that workspace. Several CLI sessions in one project are one agent area, one instance area, and N actors. The names collide easily; an actor id is never a workspace and never a class.

4 · Requirements — identity and addressing

Who is asking, and which orders they may take

MA-1

The server derives the actor; no model ever supplies one

An earlier draft had every write call take actor: string. That contradicts principle 3 and repeats the derived-key finding: anything a model names, a model can get wrong — two sessions choosing the same id, or one session inventing a second identity for itself, and claim arbitration quietly stops meaning anything.

It does not need to be supplied. A stdio MCP server is the session: one process per claude invocation, per OpenWorker session, per Kiro run. The server mints its actor id at boot and stamps every call it makes. The model never sees it, cannot collide with it, cannot rename itself. Under a shared broker the stdio side is still per-session, so the proxy mints it there instead.

The id lives for the life of the process and is written to the instance registry (MA-21), so a dashboard can name a session that is still running and mark one that is gone.

where bin/polyflow-mcp.mjs mints on boot · daemon.mjs stamps begin/report/dispatch · actor leaves four tool schemas
MA-2

A workflow declares roles, and addresses each effect kind to one

In polyflow.workflow.json, a roles map and a role on each entry of tools. An effect kind with no role is addressed to the run’s starting actor (today’s behaviour, so existing workflows load unchanged). A role may carry max_concurrent, the number of its orders that may be claimed at once; a kind (agent or human) or an agent_area, which restrict who may claim it; and a lease override. A role addressed to a pool that cannot satisfy its constraint is refused at admission, not at run time.

"roles": {
  "gatherer": { "description": "reads tickets, drafts triage",  "max_concurrent": 3 },
  "reviewer": { "description": "a person", "kind": "human", "lease": "8h" }
},
"tools": {
  "fetch_tickets":    { "tool": "github_search_issues", "role": "gatherer", "why": "…" },
  "request_approval": { "tool": "ask_user",             "role": "reviewer", "why": "…" }
}
where library.mjs _read · the admission gate refuses a tools entry whose role is undeclared
MA-3

Roles come from the process environment, never from a tool argument

An earlier draft had workflow_attach { roles[] }. That is MA-1’s hole one level up: a session that declares its own roles can attach as reviewer and satisfy its own approval gate. Anything a model can say, a model can say wrongly.

Roles are read from the server’s environment at boot, beside its minted actor id: POLYFLOW_ROLES=gatherer,reviewer. A project’s .mcp.json pins them for every session in it; an ambient variable overrides for one — POLYFLOW_ROLES=reviewer claude is how you run one terminal as the reviewer.

workflow_attach therefore takes no arguments. It reports: this actor’s id, the roles it holds, the capabilities its host binds, and the workflows it can take orders from. Useful for orienting a session, incapable of changing anything.

OpenWorker’s personas/ and teams/ and Kiro Crew’s members are where an integrator sources that environment; for a CLI session it is a shell variable.

where bin/polyflow-mcp.mjs reads POLYFLOW_ROLES on boot · a small in-store actor registry keyed by instance area, so a restart forgets nothing
MA-4

Orders are offered by role, not by run

New tool workflow_next { instance? } returns open, unclaimed orders whose role the calling actor may play and whose capability its host binds (MA-19) — across every active run in the instance area, or one run if named, and including the children of a parent. This is what lets a pool of gatherers drain a fan-out without anyone assigning work: each asks for the next order it is allowed to do. workflow_state keeps returning the whole run, with each order’s role and claim shown.

where broker.mjs open() gains a role filter · RUN_VIEW work orders gain role, claimed_by, claimed_until
MA-5

Children derive their keys from the data that spawned them

The descriptor’s children map names each child workflow and its key policy, resolved from the spawn payload exactly as a run key is resolved from start input. The child instance id is polyrun’s hash(parent, childKey, seq) (kernel.mjs:498). A duplicate spawn key in one step is already a poison (kernel.mjs:493); a duplicate across steps re-attaches to the existing child. No agent ever names a child.

"children": {
  "triage-ticket": { "workflow": "triage-ticket", "key": { "template": "{ticketId}",
                     "fields": { "ticketId": { "pattern": "^\\d+$" } } } }
}
where library.mjs parseKeyPolicy reused · effects.cjs emits {kind:'spawnChild', machineId, childKey, initData, onComplete} as polyrun FR-8.1 already defines
MA-18

A person is an actor, and how their answer arrived is recorded

A human participates as human/{id}: claims an order addressed to a human role, reports, is journaled. polycrew authenticates nobody — the host already knows who resolved an Inbox item, and authentication belongs where the identity lives. What polycrew records is which channel the write came through.

Two provenances, and they are not the same claim:

  • asserted — an agent claimed the order, asked a person through its own tool, and reported the answer. The record is the agent’s word for it.
  • verified — the write arrived from the host’s answer channel with the person’s identity attached, not through a model.

Both are legitimate; only one is evidence. A workflow that cares says so in its invariants (MA-13), and the weaker path stays visible instead of being silently equivalent — the same discipline the emission checker applies everywhere else.

The integration is small and uses what hosts already have. On OpenWorker, the path that resolves an Inbox item dispatches into the run rather than returning to the agent: workflow_signal { instance, action, data, actor: "human/jjdub" }, marked verified because it came from that channel. An agent reporting ask_user’s result is marked asserted. Nothing else changes.

where daemon.mjs dispatch gains provenance beside actor · a host adapter, not a polycrew feature
MA-19

A work order names a capability; a host profile binds it to a tool

Today a tools entry names the tool literally — Bash, github_search_issues, ask_user. Those are one host’s names. Bash is Claude Code’s; OpenWorker’s shell tool is called something else, Kiro’s something else again. So an order naming Bash cannot be worked by an OpenWorker session, and the same run cannot be shared across hosts — which is the whole interoperability claim.

An effect kind therefore names a capability, and a small per-host profile binds capability to tool name. The workflow stays portable; the binding is deployment configuration, beside the store path and the areas.

// workflow — portable
"tools": { "deploy_prod": { "capability": "shell", "role": "operator", "why": "…" } }

// host profile — deployment
{ "host": "claude-code", "bind": { "shell": "Bash", "ask_human": "AskUserQuestion" } }
{ "host": "openworker",  "bind": { "shell": "run_command", "ask_human": "ask_user" } }

A capability with no binding for the calling host means the order is simply not offered to that actor — the same question role filtering already asks, and the same answer: can this actor do this order? A workflow whose capabilities no attachable actor can satisfy is refused at admission, not discovered at 3am.

The literal tool field stays accepted and means “this host only”, so existing workflows load unchanged.

where library.mjs _read · a profile beside POLYFLOW_WORKFLOWS · broker.open() filters on capability as well as role
5 · Requirements — claiming and leases

An order belongs to one actor at a time, and only until it stops working

MA-6

Claim before you run

New tool workflow_claim { order_id }. Success returns the order with claimed_until. A second claim on a claimed order returns claimed-by-other with the holder and expiry — a result, not an error, and the model is told to call workflow_next instead. A role’s max_concurrent is enforced here.

The claim is stored on the polyrun outbox row: claimed_until already exists; this adds claimed_by. Nothing is in process memory that a crash would lose.

where broker.mjs · store.mjs additive column (the migration path at store.mjs:105 exists for exactly this)
MA-7

A claim is a lease, extended by heartbeat, lost by silence

The broker already extends the intent lease on a timer while an order is parked (broker.mjs:36). Under claims, extension happens only while the claiming actor is alive: a call from that actor on that order — workflow_state, a progress note, the report itself — renews it. A role may override lease, and a role of kind: "human" is exempt: a person is silent for hours by definition, so a human-held order is bounded by the workflow’s timer (MA-11) and never re-offered on lease expiry. Re-offering a review because the first reviewer went to lunch is not a recovery, it is a second reviewer. For agent roles, an actor that goes silent past claimed_until loses the order; it returns to unclaimed and is offered again with attempt+1, exactly the re-offer polyrun does today after a worker crash. Default lease leaseMs (5 min) stays; a role may override it.

where daemon.mjs leaseMs · broker heartbeat becomes actor-driven
MA-8

Only the claimant reports, and a late report is a result

workflow_report from an actor other than the claim holder is refused with not-your-order. A report from the holder after its lease expired and the order was re-claimed by someone else is order-expired — the existing reply (broker.mjs:73). If nobody re-claimed it yet, the late report is accepted and the claim closes: the work was done, and the completion action’s dedupe ({intentId}:done) guarantees it cannot be applied twice even if the re-offered copy is later reported too.

MA-9

Progress is a journaled action, not a chat message

A long order may report progress: workflow_report { order_id, progress: {…} } without ok. It renews the lease and dispatches the manifest’s optional onProgress action into the machine with the payload as data. A workflow that declares no onProgress gets the lease renewal and a journal row of kind progress, and nothing else. Progress is therefore visible in workflow_state to every other actor, and in the journal forever.

where effects.manifest.json per-kind onProgress · a progress row carries no state change, like a rejected step (FR-2.5)
MA-22

The broker is elected, not deployed

The first polyflow process to start on an instance area binds that area’s derived port (MA-21), opens the store, and runs the polyrun workers. Every later session finds it through the registry and proxies its MCP calls to it over loopback. Binding the port is the election — the operating system hands it to exactly one process, so there is no consensus protocol, no leader lease, and nothing to configure.

What this buys, against the two routes it replaces:

  • Nothing is installed. No service, no container. The broker is whichever claude session started first; the second is a client. From the user’s side it is still one entry in .mcp.json.
  • SQLite stays. The reason to reach for Postgres was many writers. Under election there is exactly one, so node:sqlite remains inside polyrun’s supported envelope instead of outside it.
  • No orphaned handlers. Only the broker runs effect handlers, so a parked promise is never stranded in another process. The _journaled(row, ’:done’) fence stays what it was built to be — crash recovery — rather than a routine path.
  • The dashboard is free. Same process, same port, already specified (MA-20, MA-21).

Recovery needs nothing new. The broker dies, the port frees, the next proxied call fails, that client retries and either finds a new broker or becomes one. Orders live in the store; leases expire and they are re-offered with attempt+1, which is the model already in MA-7.

Orders get their own table. A pf_orders row — instance, intent id, kind, payload, role, capability, claimed_by, claimed_until — rather than reusing the outbox row. The outbox lease belongs to polyrun’s worker and covers the effect; the claim belongs to an actor and covers the order. They are two different leases on two different things, and conflating them makes both mean less.

where bin/polyflow-mcp.mjs boot: try to bind, else proxy · store.mjs adds pf_orders · the registry (MA-21) is the discovery path
6 · Requirements — synchronization

Waiting is a state the checker has seen

There is no barrier API. A workflow that needs several things done before it continues models a state that waits, acceptors that count, and a timer that bounds the wait. polyflow adds nothing here; it inherits polyrun. The requirements are about what the admission gate must establish before such a workflow may load.

MA-10

Fan-out is spawnChild; join is the parent counting completions

The parent’s mapper emits one spawnChild per unit of work when it enters its fan-out state. Each child’s terminal state dispatches the parent’s onComplete action with {childKey, childState} (kernel.mjs:364), deduped by child id. The parent’s acceptor for that action increments a counter, records the outcome, and moves to the next state when its rule is met — all of them, a quorum, the first success. The counter and the rule are contract state, so they are in the journal and in the checker’s reach.

// parent acceptor — the join, as verified logic
TRIAGED: (model) => (p, { reject, next }) => {
  if (model.briefState !== 'joining') return reject('stale-completion');
  if (model.triaged.includes(p.childKey)) return reject('duplicate-completion');
  next.triaged = [...model.triaged, p.childKey];
  next.briefState = next.triaged.length === model.spawned ? 'drafting' : 'joining';
}
MA-11

Every join has a deadline, and the deadline is a timer

A state that waits on completions must also arm a timer intent on entry, whose action moves the run out of the wait — to a degraded path, to a review, to failure. The admission gate refuses a workflow with a waiting state and no timer out of it. This is the polyrun doctrine (FR-4.2, staleness handled by the machine) applied as a rule: a run must not be able to wait forever on an agent that never comes back.

where library.mjs certify() · a new structural check over the mapper: each state that is entered by a completion-awaiting transition emits a timer
MA-12

Cancellation flows down, never sideways

A parent that reaches a terminal state dispatches onParentTerminal into each non-terminal child (FR-8.4). A child that rejects it is journaled and surfaced, not forced. An actor holding a claim on an order of a cancelled child sees the order vanish from workflow_next and gets order-cancelled if it reports. No actor may cancel another actor’s order; it may only signal the machine, which decides.

MA-13

The rules that span parent and children are checked before load

A crew workflow ships invariants.compose.mjs alongside effect-invariants.mjs. The admission gate runs polyrun check-product over the parent × child product with those invariants; a violation or a BOUNDED verdict refuses the workflow, as the emission check does today (library.mjs certify). The sentences this makes approvable are the multi-agent ones:

{ name: 'no-post-before-every-child-terminal',
  pred: (joint) => joint.parent.briefState !== 'posting' ||
                   joint.children.every((c) => c.terminal) },
{ name: 'two-distinct-verified-reviewers',
  pred: (joint) => joint.parent.briefState !== 'posting' ||
                   new Set(joint.parent.approvals
                     .filter((a) => a.provenance === 'verified')
                     .map((a) => a.actor)).size >= 2 },
{ name: 'no-orphan-child-when-parent-terminal',
  pred: (joint) => !joint.parent.terminal || joint.children.every((c) => c.terminal) }

The second one is the DAAO two-person rule, and it is only expressible because approvals carry the actor and how it was established (MA-18). Counting actors alone would not do it: if an agent claims the approval order and reports what a person told it, the actor on the row is the agent, so two approvals routed through two sessions satisfy the rule even when the same person answered both. That is the point of putting identity on the wire — and of recording how it got there.

limits, stated check-product handles one level of children; grandchildren and joint mid-flight seeding are open (composition-plan.md). A crew workflow that spawns grandchildren is refused at load until that closes.
7 · Requirements — reporting

The journal already knows what happened. Now it knows who, and it can say so.

MA-14

Journal rows carry actor and order

Three additive columns on pr_journal: actor, order_id and provenance (MA-18). A completion dispatched by the worker after a report carries the reporting actor; a signal carries its caller; a timer carries system/timer; a child completion carries system/child:{childKey}. workflow_journal returns both fields, and accepts scope: "tree" to interleave the children’s journals by wall-clock time.

where store.mjs insertJournal · kernel dispatch signature gains an actor in the same way it carries actionId
MA-15

A progress view over the tree, computed from snapshots

New tool workflow_progress { instance } returns, for a parent: its state, each child’s state and whether it is terminal, every open order with its role and claimant, the orders whose lease is past due, the timers armed and when they fire, and the count of refused steps since the last accepted one. It is a read over snapshots and outbox rows (FR-5.2); it never touches a module. This is the coordinator’s view, and the human’s.

{ "instance": "cowork|acme|customer-brief-crew|2026-08-26",
  "state": { "briefState": "joining", "spawned": 3, "triaged": ["41","47"] },
  "children": [ { "key":"41","state":"triaged","terminal":true },
                { "key":"42","state":"reading","terminal":false,
                  "orders":[{ "order_id":"…","role":"gatherer","claimed_by":"cowork/a2","claimed_until":"…" }] },
                { "key":"47","state":"triaged","terminal":true } ],
  "waiting_on": ["42"], "timers": [{ "key":"joinWindow","fires_in_ms":1_140_000 }],
  "overdue": [], "refused_since_last_accept": 0 }
MA-16

A run report is rendered from the journal, by polyflow, with no model

New tool workflow_report_run { instance, format: "json" | "md" }, available once the run is terminal. It is a pure function of the journal tree: the timeline of accepted steps with actor and order; per-actor tallies (orders claimed, completed, lost to lease expiry, refused reports); every rejected step with its reason; timers that fired and what they did; children spawned, completed, cancelled. It is stamped with the workflow’s certificate hash and the run’s instance id, so the same run renders the same report on any machine — the polyviz discipline applied to prose.

A workflow may additionally emit a narrate effect on reaching terminal — a work order for a reporter role whose payload is the rendered report. An agent writes the human summary; that summary is reported back and journaled like any other result. The narrative is an agent’s work product; the record it summarizes is not.

MA-17

Hosts are woken by events, not polled by agents

Journal fan-out (polyrun FR-7.5, M2) publishes committed rows. polyflow subscribes and emits host events: order-available:{role}, join-opened:{instance}, run-terminal:{instance}, lease-lost:{actor}. On OpenWorker these are selfwake.wake_on_event keys (FINDINGS-phase0: integrate with selfwake, not around it); on Kiro Crew and NeMo they are whatever the host offers, and where the host offers nothing, workflow_next remains the fallback. An idle gatherer wakes when a child needs it; a coordinator session wakes when the join opens.

Hosts differ, and the spec should not imply parity. OpenWorker has selfwake, so a session genuinely sleeps and is re-invoked. Kiro Crew has heartbeats and schedules. Claude Code has neither: a CLI session is either inside a turn or waiting for a person, so for it the honest story is workflow_next at the top of a turn, and the dashboard (MA-20) is where a human sees what is waiting between turns.

MA-20

A dashboard at localhost:PORT/dashboard, for the person in the loop

Agents pull orders. A person does not, and should not have to ask an agent what is waiting for them. The daemon serves a read view over the same snapshots and outbox rows workflow_progress reads (MA-15) — no module is loaded, no model is called, nothing is computed that the journal does not already contain.

It answers two questions, in that order:

  • What needs me. Every open order whose role is kind: "human", with the run it belongs to, what it is asking, how long it has been waiting, and when its timer fires. This is the page’s reason to exist.
  • What is happening. Runs in flight with their state and their children, orders claimed and by whom, leases past due, timers armed, refused steps since the last accepted one. Terminal runs link to their rendered report (MA-16).

Answering is a write, and writes are loopback-only. A human order can be answered from the page; that dispatch is verified because it did not come through a model. Bound to 127.0.0.1 by default. Reachable from another machine means read-only: visibility for a remote colleague, while the approval path stays where authentication already lives — the host’s own answer channel (MA-18).

Stated limit. There is no authentication. The page asks for a name once and stamps it; nobody checks that the name is that person. On loopback that is the same trust as a shell on the machine. Anything stronger — an identity provider, signed approvals, per-role authorization — is an enterprise concern and is not in this spec. A deployment that needs it should not expose the write path at all.

where the daemon’s HTTP surface · polyrun already ships a read-only UI at GET / (bin/polyrun-api.mjs); this is that idea with roles, claims and the human queue
MA-21

Several crews on one machine, each with its own store, port and identity

A crew is one instance area: one store, one broker, one dashboard. Several on a machine is normal — two projects, a work crew and an experiment — and they must not see each other.

  • The store is the boundary. Two crews on one database are one crew. The daemon refuses to start on a store another live daemon holds, naming the holder rather than corrupting quietly.
  • The port is derived, not chosen. A stable hash of the instance area into a fixed range, so the same crew is the same URL every day and two crews never collide. --port overrides; a taken port is an error, never a silent shift.
  • A registry makes them findable. ~/.polyflow/instances.json maps instance area to port, store, workflow directory, pid and start time. Written on boot, entries whose pid is gone reaped on read. It is what lets a session find its own crew without configuration, and what lets one dashboard link to the others on the machine.

A person on another host reaches one crew’s dashboard read-only, or an index that lists them. Nothing is discovered across machines: the registry is a local file, not a service.

Nine tools, three of them new

Ten tools, not nine — workflow_report_run is the tenth. No tool takes an actor: the server stamps its own (MA-1), so the schemas shrink rather than grow. Read-only annotations stay as they are (tools.mjs:17); the four new write tools are WRITE with idempotentHint on attach and claim. Beside the tools the daemon serves the human dashboard (MA-20) — not a tool, and no agent calls it.

9 · The example

customer-brief-crew — the demo, with hands

The existing customer-brief becomes a parent that fans out one triage-ticket child per ticket to a pool of gatherers, joins when every child is terminal or the join window closes, drafts, then asks for approval from two distinct people — a reviewer role of kind: "human", answered through the host’s channel and therefore verified — before posting. Its guarantees, as the gate would list them:

[polyflow] admitted: customer-brief-crew
[polyflow]   emission   at-most-one-post-per-path · no-post-without-prior-approval · exactly-one-fetch-when-started
[polyflow]   product    no-post-before-every-child-terminal · two-distinct-verified-reviewers · no-orphan-child-when-parent-terminal
[polyflow]   structure  every waiting state arms a timer · every tools entry names a declared role
[polyflow]              every role constraint is satisfiable by an attachable actor
[polyflow] REFUSED: crew-no-deadline
[polyflow]   joining has no timer out — a run could wait forever on a gatherer that never returns

The measurement that would go with it is the phase-3 one, repeated with a pool: three gatherers on a four-ticket day, one of them killed mid-order. The claims are what should carry the result — the killed gatherer’s order re-offered after its lease, taken by another, one triage per ticket in the journal, and the report naming who did which.

10 · What it will not do

Named so nobody builds it by accident

Agents do not message each other

There is no channel between actors. An actor that wants another actor to know something signals the machine; the machine’s state is what the other actor reads. Anything else would be coordination the checker never saw.

No shared scratchpad

Intermediate artefacts an order produces go in the report result, which becomes action data, which becomes state. If it is too large for state, it is a reference the state carries. The run is the only shared thing.

polycrew does not create participants

There is no spawnActor. A run fans out work — child runs whose orders wait for whoever is attached with the right role — never workers. Instantiating an agent from a definition, or paging a person, is an outward act that belongs to the host; a workflow that needs one emits an ordinary work order for it and records the actor id that comes back. If nobody attaches, the join’s timer (MA-11) is what ends the wait.

No dynamic roles or negotiation

Roles are declared in the workflow and fixed at admission. An actor cannot promote itself, and a run cannot invent a role. Who may do what is part of what was checked.

No model on any coordination decision

Order routing, claim arbitration, join detection, duplicate rejection, report rendering: all deterministic, all replayable from the journal. A model only ever decides how to fulfil one order.

11 · Plan

Three milestones, each measurable with the phase-3 harness

C0 is the MVP and it is deliberately smaller than C1. The target is several Claude Code CLI sessions on one run: one host, one tool vocabulary. That needs neither roles nor capability binding — both exist for heterogeneity — and no children, no join, no product checker, no reports, no human writes. Every piece of it is on the path to the rest rather than thrown away.

C0 — the MVP

two CLI sessions, one run
  • The seam first, in polyflow, before polycrew exists: Polyflow takes an injected broker; makeTools accepts extra definitions. A substitute broker driving a run end to end is the proof. §0b
  • Elected broker, the instance registry, and pf_orders. MA-21, 22
  • Server-minted actor ids; claims, leases, arbitration; workflow_next and workflow_claim; the actor journal column. MA-1, 4, 6–8, 14
  • Dashboard, read-only. MA-20
  • Measure: two claude sessions in one project on a run with several open orders. One completion per order, two distinct actor ids neither session chose, and after killing one mid-order its claim expires and the other takes it — visible in the journal and on the dashboard.

C1 — hands

roles and other hosts
  • One broker per instance area — the prerequisite for everything else. Settle the route first (§0b): either the MCP server becomes a daemon with a streamable transport and the stdio binary a thin proxy, or claims and completions go through a Postgres store and stdio stays. Build the second if it holds; it keeps polyflow’s zero-infrastructure install intact.
  • Roles from the environment and capability binding in the descriptor — what a second host or a person makes necessary; workflow_attach; human actors and provenance; dashboard writes on loopback. MA-2, 3, 9, 18, 19, 20
  • Journal provenance beside actor and order. MA-14, 18
  • Measure: an approval order only a kind: "human" role may claim, answered from the dashboard and marked verified; and the same order refused to an agent session holding no such role.

C2 — crews

fan-out and join

  • The gate grows two checks: waiting states arm timers; check-product over invariants.compose.mjs. MA-11, 13
  • workflow_progress and the dashboard — loopback-writable, read-only beyond it. MA-15, 20
  • Measure: customer-brief-crew, n=8, three gatherers, one killed; and its refused twin with the deadline removed.

C3 — the record

reports and wake-ups

  • Measure: the same run rendered on two machines is byte-identical; a coordinator session with no polling wakes exactly once per join.
